SourceFile.HasIdentifier 性能优化续查，2026-10-27（Asia/Shanghai）



本轮得到一个不修改 Go runtime 的自适应实验方案。它同时处理“过滤判断增加成本”和“过滤后 map 变小、查找反而变慢”这两个问题。局部性能与内存结果见下文；完整 npx hereby validate 已通过。实际项目的结果单列，不能用微基准的百分比代替整体编译收益。



方案保留 SourceFile 的字段布局、sync.Once 初始化与 Go 原版 map。TextCount 不超过 64 的文件直接使用原保留规则并跳过叶节点的通用遍历。其余文件先进行有上限的探测：最多 64 个文本叶节点、256 个总节点。探测期间先按原规则插入文本；若发现第 9 个不同文本，map 已经长大，清空它并按名称位置规则重新收集；Go 1.27 的 clear 会保留已经长大的表示。若探测预算耗尽时仍不超过 8 个不同文本，则继续使用原规则。若探测已经遍历完整个文件，就直接返回已有集合。



这里有一项有意的策略变化：小文件或短前缀中不同文本较少的文件继续保留普通字面量。重复一万次同一个字符串通常只占一个 map 条目，删除它节省很少，却可能增加处理成本。这个方案并不承诺所有文件都过滤。进入过滤模式时，沿用之前的名称位置规则，保留声明名、计算属性名、元素访问与导入导出/JSDoc 模块名等。



之前全局预留容量 9 的方案会让小缓存从 256B 增至 504B。本方案只复用原本就已长大的 map：不同值案例分配 712B，重复值案例仍为 256B；没有新增 SourceFile 字段、没有自定义小数组缓存，也没有改动 GOROOT 源码。Go 1.27 Clear 中保留 directory 的实现已核对。这是依赖当前 Go map 实现的性能选择，不是 Go 语言规范提供的长期性能保证。



本轮主对照使用同一个测试二进制：原收集器从干净基线逐字复制到测试辅助函数；候选调用真正的生产收集函数。两者共享同一份 HasIdentifier、Go runtime、解析输入与热查询循环，从而减少不同二进制布局对小百分比差异的影响。GOMAXPROCS=1，固定 CPU 2，8 对交替顺序测量，收集器每次 350ms；进程 CPU 时间由循环外 getrusage 取得。构建使用原版 Go 1.27.3，-gcflags=all=-dwarf=false 仅用于控制调试信息与构建缓存体积。

上表必须结合区间和 noEmit 对照解读。noEmit 通常不初始化该缓存；若它也出现相近变化，就不能将差异直接归因于 HasIdentifier。这轮只测单线程项目，不能据此推断默认并行构建在所有机器上的收益。局部回退改善也不等于整个编译器会按相同比例提速。



第一批 compiler fixture 的约 +12% 是实际测到、且当批区间不跨零的退化信号，不能直接丢弃。因此额外进行了 6 对交替顺序复测，同时加入同项目 noEmit 对照，使用相同二进制、输入与最小 CLI 参数。结果方向反转：

compiler-fixture/emit 复测：CPU 4.3520 → 3.8734s，-11.00%，区间 [-18.15%, -4.10%]。

compiler-fixture/noemit 复测：CPU 2.2489 → 2.6371s，+17.26%，区间 [+1.61%, +27.79%]。

这两批相反的 emit 结果，以及不使用本缓存的 noEmit 同样出现较大差异，说明当前整编对照缺乏稳定归因；不能把第一次 +12% 宣称为已确认的收集器退化，也不能把复测约 -11% 宣称为优化收益。各批结果均保留，没有选择较有利的一批作为结论。

随后使用 CLI 自带 --pprofDir 进行单独 CPU 剖析，不将带剖析的运行混入计时。原收集器在约 4.79 秒 CPU 样本中累计约 60ms（1.25%），候选在约 4.40 秒样本中累计约 40ms（0.91%）。这几个样本点不足以精确解释两者的 20ms 差值，但说明这项优化直接覆盖的整编 CPU 预算是约 1% 的量级，不能从其局部微基准推导出 10% 的整编提速。阶段诊断的文件/标识符/类型/实例化计数一致。剖析文件和符号化文本位于 fixture-profiles/，诊断与复测明细位于 fixture-*.txt、fixture-recheck-summary.json。
